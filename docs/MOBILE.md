# 拾缘 · 手机应用端可行性与工作量评估

> 评估稿 · 2026-11-01（2026-11-02 增补横屏口径）
> 结论先行：**不是"套个壳"那么简单，但也远不到重写。** 推荐「现有 Web 前端移动化 + Capacitor 原生壳」路线。正式可上架版本：竖屏优先约 **58–91 人日**；**锁定横屏只需 49–80 人日**（建议优先选横屏）。若只求手机浏览器能玩：竖屏 40–60 人日 / 横屏 31–49 人日。另加商店合规/版号的非技术等待时间。

**技术复杂度构成：前端适配约 60%，壳与分发约 25%，后端配合约 15%。** 最大变量不是代码，是战斗屏在手机上的布局取舍，以及国内上架的游戏版号/备案流程。

> **横屏口径是本轮新增的重点。** 实测表明当前桌面布局在手机横屏下并没有自动变好用（见 §2.5），但横屏只需维护一套布局、且战斗屏本来就是按横屏设计的，因此比竖屏优先便宜约 9–11 人日。若确定上手机 App，推荐直接锁定横屏（A2/B2），把竖屏留给 H5 过渡页或干脆不做。

## 2. 现状盘点（为什么需要这些工作量）

### 2.1 前端体量

- `web/` 下 JS/CSS/HTML 合计 **17,861 行**：玩家端 JS 约 1.0 万行 + 独立 admin 后台 1,497 行，CSS 约 5,500 行（`style.css` 单文件 4,059 行），HTML 875 行。
- 一级界面 **15 个**：顶栏 6 屏（主城/缘阁/名册/出征/行囊/坊市）+ 扩展 8 屏（洞府/历练副本/登仙塔/成就/羁绊/缘器阁/物志/虚境）+ 隐藏图鉴 1 屏；另有战斗、结算、登录、新手教学、初始大礼包等全屏层。所有屏幕由 `web/js/core.js` 的 `TABS` / `TABS_NEW` / `TABS_HIDDEN` 动态生成，没有独立 HTML 页——移动化是改渲染分支，不是重做页面。

### 2.2 有利条件（不用重做的部分）

- **后端协议可直接复用**：约 70 个玩家业务动作全部收口在 `/api/action` 单入口（抽卡/养成/战斗/商店/活动/副本/塔……），另 23 个 GM 操作用 `/api/admin`；界面数据统一来自 `/api/boot`。手机端不需要新的服务端 API 体系。
- **战斗引擎在服务端**：C# .NET 8 的 `battle-repl` 3 进程池负责全部结算，前端只按事件流回放。手机端**不需要移植战斗内核**——这是本项目做手机端最大的有利条件。
- **内容数据驱动**：`content/` 为源、`data/` 为构建产物，换端不改玩法数值。

### 2.3 不利条件（主要工作量所在）

| 项 | 现状 | 影响 |
|---|---|---|
| 响应式断点 | 仅 8 个 `max-width` 档位（1500/1180/1120/820/760/720/680/620），主要服务窄桌面 | 手机 390–430px 宽度基本未覆盖 |
| 横屏断点 | 无 `orientation` 查询；`max-height` 最小只到 620px | 手机横屏 375–430px 高度完全未覆盖（实测见 §2.5） |
| 安全区 | 无 `viewport-fit=cover`、无 `safe-area-inset` | 横屏刘海与底部手势条会遮挡按钮 |
| 桌面工作台 | `min-width: 1121px` 才启用"锁一屏"网格，窄屏退回普通文档流 | 名册/图鉴/多栏布局在手机上会散架或出现横向滚动 |
| 触屏交互 | 全项目 `touchstart` 仅 1 处（新手教学）；`dragstart` 共 4 处（编队 3 + 教学 1） | 拖拽、长按、点按说明全部要重做 |
| hover 依赖 | `style.css` 59 条 `:hover`，扩展 CSS/JS 另有 21 条（合计 80 处） | 触屏没有 hover，说明/反馈要换成点按或长按 |
| PWA 能力 | 无 `manifest`、无 service worker | 不能"添加到主屏"、不能离线缓存 |
| 资源体积 | `web/` 内图片约 49.8MB + 音频约 72.0MB（合计约 121.8MB，≈116.1 MiB） | App 首包必须 CDN + 按需分包，不能整包塞进安装包 |
| 战斗屏布局 | 左战况 250px + 中间棋盘 + 底部技能条，按桌面横屏设计 | 竖屏放不下，必须定横屏或重排，是最大不确定项 |

### 2.4 390×844 竖屏实测（上一轮验收）

以 iPhone 14 逻辑分辨率 390×844 打开登录后的主城首屏，实测结果（上一轮记录截图路径 `.agent/screenshots/mobile-home-390.png`，该目录现已不存在，结论按上一轮记录保留；本轮重测的横屏数据见 §2.5，均有新截图）：

- **横向溢出**：页面内容宽于视口，右侧「今日」栏与「下一站」卡片被裁切，需要横向拖动才能看全——这是桌面固定栏布局在手机上最直接的症状。
- **顶栏两排导航**：6 个主 Tab + 8 个扩展入口在 390px 下挤压换行，图标与文字开始堆叠。
- **卡片栅格**：主城三栏没有降为单列，卡片按桌面宽度排版。

> 结论：现状不是"差一点适配"，而是**手机竖屏完全不可用**。第 4 节第一期的「基础框架 + 15 屏适配」两项（19–28 人日）就是消掉这张截图里的问题。

### 2.5 手机横屏实测（844×390 / 932×430 / 667×375，本次新增）

用 Chromium 移动仿真（`deviceScaleFactor=2`、`screenOrientation=landscapePrimary`）打开登录后的真实页面，逐屏测量。原始数据：`target/_mobile_landscape_report.json`，截图：`target/shots/mobile-landscape-*.png`。

| 视口 | 屏 | 顶栏高 | 页面内容高 | `#resBar` 实际位置 | 关键结论 |
|---|---|---:|---:|---|---|
| 844×390（iPhone 14 横屏） | 主城 | 106px（27%） | 1335px | left=860 → right=1328（**整条在视口外**） | 资源栏不可见，首屏只能看到左栏上半截 |
| 844×390 | 名册 | 121px（31%） | 2745px | 同上，整条在视口外 | 390px 高只能看到编队条顶部；`tapSmall=66` |
| 844×390 | 出征 | 121px（31%） | 743px | 同上，整条在视口外 | 首屏只能看到章节头 + 第一排关卡 |
| 844×390 | 战斗 | 0（全屏层） | 390px | — | 战况栏 250px；棋盘区仅 **524×98px**；底部技能区 176px（45%） |
| 932×430（iPhone 15 Pro Max） | 主城 / 名册 / 出征 | 97–112px（23–26%） | 1335 / 2382 / 743px | left=860–1328（只露出 72px，其余被裁） | 比 844 略好，但资源栏仍不可用 |
| 932×430 | 战斗 | 0 | 430px | — | 棋盘区 **612×138px**，仍不足 |
| 667×375（iPhone SE 横屏） | 主城 | 138px（37%） | 1335px | 同样在视口外 | 顶栏占屏高超过三分之一 |
| 667×375 | 战斗 | 0 | 375px | — | 棋盘区仅 **458×49px**，几乎不可见 |

> 资源栏在三档视口下横坐标恒为 left=860 / width=468 / right=1328——与视口宽度无关，说明它是被桌面 `#topbar .trow` 的 flex 布局按固定内容宽排到右侧、再由 `overflow-x:hidden` 裁掉的，不是"窄屏才出问题"。

**核心发现（四条）：**

1. **没有横向滚动条 ≠ 布局正常。** `style.css` 第 47 行 `html, body { overflow-x: hidden; }` 把所有横向溢出裁掉了，所以 `document.scrollWidth === clientWidth`（12 条记录里 0 条报横向溢出）；但 `#resBar` 实际横坐标 860–1328（视口 844/932/667 全都一样），铜钱/缘玉/体力/精力**整条资源栏在屏幕外**，玩家看不到也点不到。这是"假响应式"。
2. **顶栏太高。** 两排导航（6 主 Tab + 8 扩展入口）在横屏下占 97–153px，等于屏高的 23%–37%。横屏必须压成**单行顶栏 + 更多抽屉**，目标 ≤56px。
3. **战斗屏是最大问题。** 桌面版按 1920×1080 设计，横屏 375–430px 高度下棋盘区只剩 49–138px 高，卡牌立绘与血条都看不清；底部行动者 + 三张技能卡固定 176px（占 41%–47%）。必须做横屏专用紧凑布局（战况改浮层、棋盘撑满剩余高度、技能条压缩）。
4. **15 个一级屏在横屏下仍是桌面布局。** 名册工作台在 2382–2979px 高、出征 743px，横屏首屏（375–430px）看不到角色卡/关卡列表主体；行囊/坊市同理。横屏需要独立的一套短视口断点，不是把竖屏断点反过来用。

> **结论：当前横屏同样不可用，但比竖屏更有改造价值。** 战斗屏本来就是横向构图，横屏是更自然的方向；只要新增 `orientation: landscape` + `max-height: 480px` 断点、单行顶栏、资源栏回位、战斗屏紧凑重排，就能以比竖屏更少的工作量得到完整体验。

## 3. 四种方案对比

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| 响应式 H5 | 现有前端加移动断点 + 触屏交互 | 最快、不改架构、无商店审核 | 无推送/离线/原生支付，浏览器地址栏削弱沉浸感 | 先做，作为一切方案的地基 |
| **PWA + Capacitor 壳（推荐）** | 同一套 Web 代码，套 iOS/Android 原生壳；token 存 Keychain/Keystore，补推送与支付 | 复用 100% 前端逻辑和后端；可上架、可推送、可热更新；工作量可控 | 需处理 WebView 性能、商店合规、壳工程构建 | **正式 App 的首选** |
| Flutter / Unity / RN 重写 | 用原生框架重做全部 UI | 长期性能与手感最好 | 15 个界面 + 战斗表现全部重写，现有 1.8 万行前端作废 | 除非要换引擎，否则不划算 |
| 微信小游戏 | 换引擎适配微信小游戏运行时 | 微信流量入口 | 4MB 主包/20MB 总包上限 vs 121.8MB 资源；需重做资源与部分 API | 作为发行渠道另评估 |

## 4. 推荐路线：分两期走

### 4A. 竖屏优先路线（原基线）

#### 第一期：移动 H5 可玩版（约 40–60 人日）

目标：在主流手机浏览器里完整走通「注册 → 新手教学 → 抽卡 → 编队 → 战斗 → 结算 → 养成」全流程。

1. **基础框架**（4–6 人日）：新增 480/430/390 断点；顶栏 6 个主 Tab 改底部 TabBar（8 个扩展入口收进"更多"）；`env(safe-area-inset-*)` 适配刘海屏/底部手势条；禁止双击缩放。
2. **15 个一级屏逐个适配**（15–22 人日）：名册/图鉴从"锁一屏工作台"改为单列卡片流 + 底部操作条；表格类界面（背包/商店/成就）改卡片列表。
3. **战斗与结算屏**（8–12 人日）：确定横屏锁定方案；左战况面板改可收起浮层；底部技能条加大触控热区；终式 cut-in 动画在低端机降级。
4. **触屏交互**（3–5 人日）：编队拖拽改 Pointer Events + `touch-action: none`；80 处 hover 样式改长按/点按浮层；滚动与拖拽手势冲突处理。
5. **性能与资源**（5–8 人日）：图片懒加载 + WebP；121.8MB 资源按章节/角色分包，CDN 按需拉取；战斗特效分级（低端机关粒子）。
6. **H5 浏览器抽测**（5–7 人日）：iOS Safari / Android Chrome / 微信内置浏览器覆盖主流机型，按第 9 节验收标准过一遍。

#### 第二期：可上架 App（在第一期基础上再约 18–31 人日）

1. **Capacitor 壳工程**（5–8 人日）：iOS/Android 双端工程、启动屏、状态栏、横屏锁定、返回键、token 安全存储、外链白名单。
2. **后端配合**（5–10 人日）：登录态刷新（当前 7 天单 token）、推送通道、IAP 票据校验（如有内购）、静态资源 CDN 域名、并发压测（单 Node 进程 + 3 战斗进程池）。
3. **构建与发布**（3–5 人日）：沿用 `tools/package.mjs` 产出 Web 包，壳工程走 Fastlane/CI 双端打包；签名证书、版本号、灰度。
4. **真机测试**（5–8 人日）：iOS/Android 各 3–5 台主流机型全流程回归。

### 4B. 横屏优先路线（本次新增，推荐替代 4A）

> 前提：**App 端锁定横屏**（`screenOrientation: landscape`），游戏内竖屏时显示「请横屏游玩」提示。H5 端同样锁定横屏，竖屏手机只给提示页。

#### 第一期：横屏 H5 可玩版（约 31–49 人日）

1. **横屏基础框架**（3–5 人日）：新增 `@media (orientation: landscape) and (max-height: 480px)`；顶栏两排压成**单行**（6 主 Tab 保留，8 扩展入口收进「更多」抽屉）；`#resBar` 从右侧溢出改为顶栏内可横向滚动/折叠；`env(safe-area-inset-*)` + `viewport-fit=cover` 适配刘海与手势条；竖屏时显示「请横屏游玩」提示。
2. **15 个一级屏横屏适配**（11–17 人日）：目标视口 667×375 – 932×430；名册/图鉴工作台从「锁一屏」改为「左侧筛选 + 中间网格 + 右侧详情」三栏紧凑版，整屏高度锁 `100dvh - 48px`；行囊/商店/成就改双列卡片；主城三栏压成两栏（左栏签到合并到顶部条）。
3. **战斗 / 结算 / 教学屏横屏适配**（5–8 人日）：战况面板改可收起浮层（默认收起，按钮唤出）；棋盘区撑满 `100dvh - 顶栏 - 技能条`；底部行动者 + 三张技能卡从 176px 压到 ≤120px；结算弹窗在 375px 高度下可滚动。
4. **触屏交互**（3–5 人日）：同 4A 第 4 条。
5. **性能与资源**（5–8 人日）：同 4A 第 5 条。
6. **横屏浏览器抽测**（4–6 人日）：iOS Safari / Android Chrome 横屏覆盖 667×375、844×390、932×430 三档，按第 9 节横屏验收标准过一遍。

#### 第二期：可上架 App（横屏，增量约 18–31 人日）

同 4A 第二期，但 Capacitor 壳工程增加**原生横屏锁定**（iOS `UISupportedInterfaceOrientations` 只留 Landscape、Android `screenOrientation="landscape"`），真机回归覆盖横竖切换。模块与工时不变（壳工程 5–8 人日已含锁定配置）。

> 第一期 H5 = 40+2+5+3 至 60+3+8+5 = **50–76 人日**；第二期不变 18–31。`node tools/mobile-estimate.mjs` 三套口径均自带对账。

## 6. 技术改造清单

### 前端
- [ ] 断点体系：新增 `@media (max-width: 480px / 430px / 390px)`；现有 1121px 的桌面锁屏逻辑在手机完全停用。横屏优先时改为 `@media (orientation: landscape) and (max-height: 480px)`。
- [ ] 导航：竖屏顶栏双排（6 主 + 8 扩展）收成底部 5 Tab + "更多"抽屉；**横屏必须压成单行顶栏（≤56px）+ "更多"抽屉**。
- [ ] 资源栏：`#resBar` 当前是 `flex: 0 0 auto`，在横屏会被推到视口外（实测三档视口下 left 恒为 860、right=1328）；横屏下需移入第二行或改为可折叠。
- [ ] 名册/图鉴：取消按容器宽高计算的 `applyFixedGrid` / `applyFillGrid`，改 CSS `auto-fill` 单列/双列卡片。
- [ ] 战斗：`web/js/battle-ui.js`（484 行）与 `battle-fx.js`（1,115 行）重点回归；**横屏下战况面板改可收起浮层、棋盘区撑满剩余高度、底部技能条压到 ≤120px**。
- [ ] 触屏：`web/js/screens-main.js` 的编队拖拽（3 处 `dragstart`）改 Pointer Events；`web/js/tutorial.js` 的 mousedown/mouseup/dragstart 同步改 pointer。
- [ ] 音频：`web/audio` 约 72MB 不能预加载，BGM/语音按需流式；首次点击解锁策略在 WebView 内同样适用。
- [ ] PWA：补 `manifest.webmanifest` + service worker（首屏壳缓存，游戏数据不缓存）。
- [ ] 横屏提示：竖屏时用 CSS 媒体查询显示「请横屏游玩」全屏提示（不依赖 JS 旋转检测）。

### 后端（`tools/serve.mjs`）
- [ ] 增加 refresh token / 滑动续期；移动端 token 存系统安全区。
- [ ] 静态资源支持 CDN 前缀或独立资源域名。
- [ ] 推送服务接入（APNs / FCM / 厂商通道）。

- [ ] 压测：单 Node 进程 + `battle-repl` 3 进程池的并发上限，手机用户在线时长通常高于桌面。

### 壳（Capacitor）

- [ ] 原生能力：安全存储、网络状态、推送、分享、返回键、横屏锁定。
- [ ] 热更新策略（可选）：Web 包独立于壳发版，便于修 bug。

## 7. 合规与发行（最容易被低估，且不占开发人日）

- **国内 Android 渠道**：需要软件著作权、ICP 备案、隐私政策、实名认证/防沉迷接入；**含内购的游戏需要游戏版号**，审批以月计，且是上架前置条件。
- **iOS 中国区**：游戏类同样要求版号；内购走 IAP，苹果抽成 30%。
- **海外发行**：可绕开版号，但要处理 GDPR/COPPA、年龄分级（ESRB/PEGI）、支付税务。
- **建议**：先用 H5/PWA 验证留存与玩法，再决定是否投入版号与双端上架；版号周期可与第二期开发并行启动。

## 8. 风险点

| 风险 | 等级 | 说明 / 对策 |
|---|---|---|
| 战斗屏竖屏适配 | 高 | 桌面为固定三栏布局，手机竖屏放不下；先做横屏原型验证，必要时重排为上下结构 |
| **横屏短视口（375–430px 高）** | **高** | **实测棋盘区仅 49–138px 高、资源栏 right=1328 被裁出所有横屏视口；必须做横屏专用紧凑布局，不能直接复用桌面样式** |
| 低端机 WebView 性能 | 中高 | `battle-fx.js` 大量 CSS 动画与 DOM 操作；需特效分级与帧率实测 |
| 121.8MB 资源首次加载 | 中高 | 必须 CDN + 分包 + 懒加载；否则 4G 首进体验不可接受 |
| 触屏交互遗漏 | 中 | 80 处 hover 样式、编队拖拽、图鉴翻页需逐屏过一遍真机 |
| 服务端并发 | 中 | 单 Node 进程 + 3 战斗进程池，上线前压测 |
| 双端存档一致性 | 低 | 存档按用户一行 JSON 存储、逐用户串行写，天然可共享；注意手机与网页同时操作时的串行写 |
| 商店审核/版号 | 高（周期） | 非技术工作，提前启动；无版号只能走 H5/海外 |
| 横屏锁定后的竖屏用户 | 中 | 锁定横屏意味着竖屏持机用户必须转屏；H5 端需提供「请横屏游玩」提示页，App 端靠系统旋转 |

## 9. 验收标准（建议）

### 9A. 竖屏优先

- [ ] 390×844 / 430×932 竖屏 + 844×390 横屏，全流程无横向滚动条、无控件被遮挡。
- [ ] 中端 Android 机战斗稳定 ≥30fps，终式动画可关闭。
- [ ] 4G 下首屏可交互 < 5 秒（首包 < 5MB，资源按需拉取）。
- [ ] 注册 → 教学 → 抽卡 → 编队 → 战斗 → 结算 → 养成 全链路真机通过。
- [ ] 切后台 5 分钟回来，登录态与战斗状态可恢复（或安全重登）。
- [ ] iOS/Android 各至少 3 台主流机型回归通过。

### 9B. 横屏优先（本次新增）

- [ ] 667×375 / 844×390 / 932×430 三档横屏下，**铜钱/缘玉/体力/精力资源栏完整可见可点**（当前实测三档 right=1328，844 视口下整条被裁出）。
- [ ] 顶栏总高 ≤56px（当前实测 97–153px，占屏高 23%–37%）。
- [ ] 战斗屏棋盘区高度 ≥180px（当前 49–138px），底部技能区 ≤120px（当前 176px）。
- [ ] 15 个一级屏横屏首屏可见主操作区，不出现"只能看到标题"的屏。
- [ ] 竖屏持机显示「请横屏游玩」提示页，不出现半截布局。
- [ ] 刘海屏左右安全区：`safe-area-inset-left/right` 内无按钮被遮挡。
- [ ] 横竖切换（App 允许时）不丢当前屏与战斗状态。

## 10. 最终结论

**做手机应用端的复杂度是"中等偏大"：**

- **不用**重写后端、不用移植 C# 战斗引擎、不用重做内容数据——这三块省掉了最大的成本。
- **主要成本**在：15 个界面的移动化重排（尤其战斗屏）、触屏交互体系、121.8MB 资源的按需加载、以及 Capacitor 壳与商店合规。
- **横屏是更划算的切入点**：只做一套横向布局，H5 31–49 人日、双端 App 49–80 人日，比竖屏优先省 9–11 人日；战斗屏本来按横屏设计，观感也更接近桌面版。代价是竖屏用户必须转屏。
- 建议节奏：**第一期 6–10 周（1–2 人）做横屏 H5 可玩版验证手感 → 第二期再 3–5 周（2 人）上壳上架**；若必须同时支持竖屏，再叠加 10–16 人日做横竖双向（合计 68–107 人日）。版号/备案同步启动，不阻塞开发但决定上线时间。
